# Модель разграничения прав доступа

## Назначение модели

Модель разграничения прав доступа предназначена для определения допустимых действий пользователей веб-информационной системы управления автопарком, строительными объектами, сервисными событиями и персоналом.

В системе используется ролевая модель доступа. Каждому пользователю назначается одна роль, которая определяет набор доступных разделов, операций с данными и возможность просмотра журналов аудита.

## Роли пользователей

| Роль | Системное значение | Назначение |
| --- | --- | --- |
| Администратор | `admin` | Полный доступ к системе, управление пользователями, ролями, справочниками, автопарком, объектами, сервисными событиями и журналами аудита. |
| Модератор | `moderator` | Оперативное управление автопарком, водителями, механиками, строительными объектами и сервисными заявками без доступа к управлению учетными записями пользователей. |
| Механик | `mechanic` | Просмотр информации о сервисных событиях, автопарке, строительных объектах и уведомлениях, связанных с эксплуатацией и обслуживанием техники. |
| Водитель | `driver` | Просмотр доступной информации о технике, объектах, уведомлениях и собственном профиле без возможности изменять системные данные. |

## Общие принципы доступа

1. Доступ к закрытой части системы предоставляется только после успешной аутентификации.
2. Аутентификация выполняется с использованием JWT-токена.
3. Информация о роли пользователя хранится в базе данных в поле `User.role`.
4. Клиентская часть использует роль пользователя для отображения доступных разделов и скрытия недоступных действий.
5. Серверная часть должна проверять права доступа перед выполнением операций создания, изменения, удаления и просмотра журналов аудита.
6. Все значимые действия пользователей фиксируются в журналах аудита.
7. Заблокированный пользователь не может войти в систему.

## Правила доступа по API

| Группа маршрутов | Назначение | Требуемая роль |
| --- | --- | --- |
| `POST /auth/login` | Вход в систему | Доступно без JWT, если пользователь не заблокирован |
| `POST /auth/logout` | Выход из системы | Любой авторизованный пользователь |
| `GET /auth/session` | Получение текущей сессии | Любой авторизованный пользователь |
| `/profile/*` | Работа с собственным профилем | Любой авторизованный пользователь |
| `GET /users`, `POST /users`, `PUT /users/:id`, `DELETE /users/:id`, `PATCH /users/:id/block` | Управление пользователями | Только `admin` |
| `GET /users/audit-log` | Журнал действий пользователей | `admin`, `moderator` |
| `/drivers/*` | Управление водителями | Чтение: все роли; изменение: `admin`, `moderator`; аудит: `admin`, `moderator` |
| `/mechanics/*` | Управление механиками | Чтение: все роли; изменение: `admin`, `moderator`; аудит: `admin`, `moderator` |
| `/fleet/*` | Управление автопарком | Чтение: все роли; изменение: `admin`, `moderator`; аудит: `admin`, `moderator` |
| `/sites/*` | Управление строительными объектами | Чтение: все роли; изменение и назначения техники: `admin`, `moderator`; аудит: `admin`, `moderator` |
| `/service-events/*` | Управление сервисными событиями | Чтение: все роли; изменение: `admin`, `moderator` |
| `/notifications/*` | Работа с уведомлениями | Любой авторизованный пользователь с фильтрацией категорий по роли |
| `/uploads/documents` | Загрузка документов | `admin`, `moderator` |

## Правила отображения интерфейса

| Элемент интерфейса | Условие отображения |
| --- | --- |
| Раздел "Пользователи" в боковом меню | Только `admin` |
| Кнопки создания, редактирования и удаления записей | `admin` или `moderator` |
| Карточки предупреждений о незакрепленных водителях, механиках и сервисных заявках | `admin` или `moderator` |
| Журналы аудита в разделах пользователей, водителей, механиков, автопарка и объектов | `admin` или `moderator` |
| Таблицы просмотра автопарка, водителей, механиков, объектов и сервиса | Все авторизованные пользователи |
| Профиль пользователя | Все авторизованные пользователи |

В клиентской части проекта данные правила реализуются через контекст роли пользователя:

| Флаг интерфейса | Условие | Назначение |
| --- | --- | --- |
| `isAdmin` | `role === "admin"` | Доступ к администрированию пользователей. |
| `isModerator` | `role === "moderator"` | Определение роли модератора. |
| `canEdit` | `role === "admin" || role === "moderator"` | Отображение действий создания, редактирования, удаления и назначения. |
| `canViewAudit` | `role === "admin" || role === "moderator"` | Отображение журналов аудита. |

## Хранение данных о доступе

| Объект | Назначение |
| --- | --- |
| `User.role` | Хранит роль пользователя: `admin`, `moderator`, `mechanic`, `driver`. |
| `User.status` | Определяет состояние учетной записи: `active` или `blocked`. |
| `Session` | Хранит активные JWT-сессии пользователя. |
| `AuditLog` | Фиксирует действия с пользователями и входы в систему. |
| `DriverAuditLog` | Фиксирует операции назначения водителей, изменения документов и категорий. |
| `MechanicAuditLog` | Фиксирует операции назначения механиков, изменения документов и специализаций. |
| `FleetAuditLog` | Фиксирует изменения автопарка и закрепление водителей. |
| `ConstructionSiteAuditLog` | Фиксирует операции со строительными объектами и назначениями техники. |
| `NotificationRead` | Хранит отметки о прочтении уведомлений конкретным пользователем. |

## Рекомендации по серверной реализации

Для надежного разграничения доступа проверки ролей должны выполняться не только в интерфейсе, но и на сервере. Рекомендуется добавить в backend отдельные элементы RBAC:

1. Декоратор `@Roles(...)` для указания разрешенных ролей на уровне контроллеров и методов.
2. `RolesGuard`, который получает роль пользователя из JWT payload и сравнивает ее с требуемыми ролями.
3. Применение `RolesGuard` совместно с `JwtAuthGuard` для всех защищенных маршрутов.
4. Возврат ошибки `403 Forbidden`, если пользователь авторизован, но его роль не позволяет выполнить операцию.
5. Покрытие правил доступа e2e-тестами для всех критичных API-маршрутов.

Пример логики проверки:

```text
Пользователь отправляет запрос -> JwtAuthGuard проверяет токен -> RolesGuard проверяет роль -> контроллер выполняет операцию -> сервис записывает действие в журнал аудита.
```

## Верификация модели доступа

Для проверки корректности модели доступа необходимо выполнить тестирование следующих сценариев:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Заблокированный пользователь пытается войти в систему | Вход запрещен |
| Пользователь без JWT обращается к защищенному маршруту | Возвращается ошибка `401 Unauthorized` |
| Водитель пытается создать технику | Возвращается ошибка `403 Forbidden` |
| Механик пытается открыть журнал аудита | Возвращается ошибка `403 Forbidden` |
| Модератор создает сервисное событие | Операция выполняется успешно |
| Модератор пытается создать пользователя | Возвращается ошибка `403 Forbidden` |
| Администратор создает пользователя | Операция выполняется успешно |
| Администратор блокирует пользователя | Статус пользователя меняется на `blocked` |
| Модератор назначает технику на строительный объект | Операция выполняется успешно, действие фиксируется в журнале аудита |
| Водитель просматривает автопарк | Данные отображаются в режиме чтения |

## Итоговая схема доступа

| Уровень | Механизм | Назначение |
| --- | --- | --- |
| Аутентификация | JWT | Подтверждение личности пользователя. |
| Авторизация | Роль пользователя | Определение допустимых операций. |
| Интерфейс | `RoleProvider`, `canEdit`, `canViewAudit`, `isAdmin` | Скрытие недоступных разделов и действий. |
| API | `JwtAuthGuard`, `RolesGuard` | Защита маршрутов от несанкционированного доступа. |
| База данных | `UserRole`, `UserStatus`, связи с журналами аудита | Хранение ролей, статусов и истории действий. |
| Аудит | Audit-таблицы | Контроль изменений и отслеживание ответственных пользователей. |
